# Nippy build, tooling, and testing

How to build the compiler, how to run and extend the test suite, and what the
build environment is expected to provide. For what the compiler *does*, see
`ARCH.md`; for the C API, `API.md`.

## Requirements

| Requirement | Notes |
|---|---|
| A C11 compiler | `cc` on `PATH`. GCC and Clang are both supported and both are clean. |
| GNU Make | `Makefile` uses pattern-free explicit rules; GNU Make 4.x is what it is tested with. |
| libc | The only library the compiler links against. |
| `cc` for generated code | The driver shells out to `cc -std=c11`, so the same compiler must be available at runtime, not just at build time. |

No package manager, no code generator, no external dependency. There is no
`configure` step and no generated source checked in.

The build machine this was last verified on: GCC 16.2.1, GNU Make 4.4.1, x86_64
Linux. Clang was also verified clean.

## Targets

```sh
make            # build bin/nippy
make example    # build bin/nippy, then compile examples/13.nip -> bin/13
make test       # build bin/nippy and bin/tester, then run the suite
make clean      # remove bin/ entirely
```

`make` is the default target and builds only the compiler. `make example` is a
smoke test that exercises the whole pipeline end to end, including the `cc`
invocation and running the produced binary. `make test` runs the real suite.

There is no `install`, `dist`, or `check` target. Shipping is a prototype
concern that has not come up yet.

## Flags

```make
CC = cc
CFLAGS = -std=c11 -Wall -Wextra -Wpedantic -O2
```

All three warning flags are part of the contract. Code must build with **no
warnings**; a warning is a failing build in review even though Make will not
stop for it. Do not silence a warning with a cast unless the cast is genuinely
correct.

`-std=c11` appears twice by design and both must stay C11: `CFLAGS` builds the
compiler, and `build_binary` in `compiler/main.c` compiles the generated C with
`cc -std=c11`. Moving one to a newer revision without the other is a bug.

Overrides go through `make` variables rather than editing the file:

```sh
make CC=clang
make CFLAGS="-std=c11 -Wall -Wextra -Wpedantic -g -O0"
```

Note that overriding `CFLAGS` on the command line replaces the whole value, so
repeat the warning flags or you will lose the contract.

## What gets built

| Artifact | Built from | Purpose |
|---|---|---|
| `bin/nippy` | `$(COMPILER_SOURCES)` + every header in `include/` | The compiler and its command-line driver |
| `bin/tester` | `tests/runner.c`, `tests/test.c`, plus `$(COMPILER_LIB_SOURCES)` | The test suite |
| `bin/13` | `examples/13.nip`, via `make example` | Smoke-test binary |
| `bin/<name>.c`, `bin/<name>.h` | Generated by `bin/nippy` | Generated C for `<name>` |

`COMPILER_SOURCES` lists every `.c` file explicitly — there is no wildcard over
`compiler/`, so **a new module must be added to the Makefile** or it will not
build. `COMPILER_LIB_SOURCES` is `COMPILER_SOURCES` minus `compiler/main.c`; the
test binary links that set so tests can call stages directly, and must not link
`main.c` because the harness supplies its own `main`.

`COMPILER_HEADERS` *is* a wildcard over `include/*.h`, so a new header is picked
up automatically as a rebuild dependency.

Both artifacts land in `bin/`, which is git-ignored. Nothing generated is
committed.

## Incremental behaviour

Make rebuilds a target when any of its prerequisites change, including headers.
That is the only incrementality that exists: any source change rebuilds the whole
compiler in one `cc` invocation, because `bin/nippy` is a single link step over
all translation units. There is no object file, no `.d` dependency file, and no
per-module caching.

Incremental *compilation* as a language feature (only recompiling the Nippy
module that changed) does not exist either. Both gaps are tracked in
`ARCH.md`'s "Known gaps" section.

## Manual checks

Useful one-liners when the suite is not enough:

```sh
# Compile-check one unit without linking (needs -Iinclude; -fsyntax-only is fast)
cc -std=c11 -Wall -Wextra -Wpedantic -Iinclude -fsyntax-only compiler/checker.c

# Build the compiler with a different toolchain
make clean && make CC=clang

# Full rebuild, no warnings anywhere
make clean && make 2>&1 | grep -iE 'warning|error'

# Run a snippet without touching the repo
printf 'var x : Int32 = 13\n' > tmp/t.nip
./bin/nippy tmp/t.nip tmp/t && ./tmp/t

# Inspect the generated IR
cat bin/13.c bin/13.h
```

Scripts, snippets, and scratch files belong in `tmp/`. See `AGENTS.md`.

## Test suite

```sh
make test
```

Run this before calling a change complete. The output is one line per test plus
a summary:

```text
PASS: var declaration of 13 compiles and prints 13
...
109 tests: 109 PASS, 0 FAIL, 0 TODO, 0 Error
```

The runner returns non-zero if any test fails or errors, so `make test` fails the
same way. A non-zero `TODO` count is not a failure.

Result kinds:

| Result | Meaning | Fails the suite |
|---|---|---|
| `TEST_PASS` | Behaviour is correct | No |
| `TEST_FAIL` | Behaviour is wrong | Yes |
| `TEST_ERROR` | The test could not run (harness problem) | Yes |
| `TEST_TODO` | Decided but not yet implemented | No |

### How a test is written

1. Add `TestResult test_<name>(void)` to `tests/test.c`.
2. Declare it in `include/test_cases.h`.
3. Register it in the `tests[]` table in `tests/runner.c`.

A test returns a `TestResult` and prints a short reason to `stderr` before
failing, so a red run says *why*. Two helpers carry most of the weight:

- `expect_diagnostic(source, what, format, ...)` writes `source`, runs the
  compiler, and asserts it exits non-zero with a diagnostic containing `format`
  rendered with the remaining arguments.
- `expect_message(buffer, size, format, ...)` renders the expected text from the
  same macro the compiler uses.

### Message coverage is a rule

Every `MESSAGE_*` macro in `include/messages.h` must be named by at least one
test, and tests must assert against the macro rather than a hand-copied literal:

```c
return expect_diagnostic("var x : Float = 13\n", "an unknown variable type",
                         MESSAGE_CHECKER_UNKNOWN_TYPE, "Float", "x");
```

This keeps wording and assertions from drifting apart. It also means a message
that cannot be reached from a test is a design smell: either the path is dead
code, or it needs a hook. Deleting an unreachable message is usually right.

### Test kinds

- **End-to-end** — write a `.nip` file, run `./bin/nippy`, run the binary,
  inspect the generated `.c`/`.h`, and check the output. Used for the positive
  cases and the driver.
- **Stage-level** — include the stage headers and call `lexer_tokenize`,
  `parser_parse`, `checker_check`, `analyser_analyse`, or `generator_generate`
  directly. Used for internal and defensive messages that no source program can
  reach, by constructing a deliberately malformed artifact.
- **Allocation-failure** — arm `nippy_alloc_fail_after(n)` and prove each
  out-of-memory path reports and exits cleanly.

### Allocation-failure testing

`compiler/alloc.c` wraps `malloc`/`realloc` with a one-shot failure hook so
out-of-memory handling stays executable instead of untested.

- `nippy_alloc_fail_after(n)` lets the next `n` allocations succeed, fails the
  one after that, then disables itself. Failing exactly one allocation at a time
  is what lets a test observe the message that failure produces; a cascading
  failure would mask it by also failing the error-message copy.
- `nippy_alloc_reset()` (or `nippy_alloc_fail_after(NIPPY_ALLOC_NEVER)`)
  disables it.
- The driver honours the environment variable `NIPPY_FAIL_ALLOC_AFTER`, which is
  a test-only interface. It must stay unset in normal use.

Two tests use this: one sweeps every allocation index and asserts the compiler
fails closed (non-zero exit, a diagnostic, no binary left behind, no crash), and
one proves each of the ten out-of-memory messages is reachable.

### Scratch files

Tests deliberately use fixed names under `tests/.test*` and `cleanup()` removes
them before and after each test. They are never written into `bin/`, so a failed
test cannot leave a stale binary that a later test picks up. If you add a test
that creates a file, add its path to `temporary_files[]` so `cleanup()` knows
about it.

## Tooling

| Tool | Used for | Notes |
|---|---|---|
| `cc` (GCC) | Building the compiler, building the test binary, and compiling generated C | Default; the driver hardcodes `cc` |
| `clang` | Cross-toolchain check | `make CC=clang` builds and tests clean |
| `gdb` | Debugging | `make CFLAGS="-std=c11 -Wall -Wextra -Wpedantic -g -O0"` first |
| `clang-format` | Formatting reference | No committed config; match the existing style by hand |

Not available in the current environment, and therefore not part of the
workflow: **ASan/UBSan runtimes and Valgrind**. `-fsanitize=address` fails at
link time here because `libasan`/`libubsan` are not installed, and Valgrind is
absent. The allocation-failure sweep is what stands in for memory-fault
detection today. If a sanitizer runtime becomes available, adding a
`make test` variant that rebuilds with `-fsanitize=address,undefined` is the
obvious next improvement — do not document it as supported until it actually
links.

## Generated-code build

`compiler/main.c` writes the generated `.c` and `.h` beside the requested output
binary and then runs:

```sh
cc -std=c11 -o <output> <output>.c
```

Points worth knowing:

- The command is assembled as a shell string with single-quote escaping via
  `shell_quote`, so paths containing spaces or quotes survive.
- Only the `.c` is compiled; the `.h` is picked up through the emitted
  `#include`, which is why the header name is validated before being
  interpolated.
- The generated header is written first, then the source. A failure writing the
  source therefore leaves the header on disk, which is harmless because nothing
  links it.
- Generated code must compile cleanly under `-std=c11 -Wall -Wextra -Wpedantic`.
  That is why unused initialised variables get a `(void)name;` line: the
  generator, not the user, is responsible for warning-free output.
- The program's own `cc` invocation does not add warning flags; the clean-build
  property is verified by tests and by manual checks, not enforced at that step.

## Continuous integration

There is none. The suite is expected to be run locally with `make test` before a
change is called complete. If CI is added, the minimum useful pipeline is
`make clean && make && make test` on both GCC and Clang.

## Known build gaps

- No sanitizer or Valgrind coverage in this environment.
- No single-test filter; `./bin/tester` always runs the whole suite.
- No test parallelism; the suite is serial and takes about a second.
- No install target and no versioned binary.
- No CI configuration.
- Incremental compilation (recompiling only the changed module) is not
  implemented at either the Make or the Nippy-module level.
