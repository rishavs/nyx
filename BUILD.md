# Nippy build, tooling, and testing

How to build the compiler, how to run and extend the test suites, and what the
build environment is expected to provide. For what the compiler *does*, see
`ARCH.md`; for the C API, `API.md`.

## Requirements

| Requirement | Notes |
|---|---|
| A C11 compiler | `cc` on `PATH`. GCC and Clang are both supported and both are clean. |
| GNU Make | `Makefile` uses pattern-free explicit rules; GNU Make 4.x is what it is tested with. |
| libc | The only library the compiler links against. |
| `cc` for generated code | The driver shells out to `cc -std=c11`, so the same compiler must be available at runtime, not just at build time. |

No package manager, no code generator, no external dependency. There is no
`configure` step and no generated source checked in.

The build machine this was last verified on: GCC 16.2.1, GNU Make 4.4.1, x86_64
Linux. Clang was also verified clean.

## Targets

```sh
make                # build bin/nippy
make test           # build everything, then run both suites
make test-compiler  # run only the compiler suite
make test-tool      # run only the tool suite
make test-list      # list every test by group
make golden-update  # regenerate the golden tests' expected output
make clean          # remove the build outputs under bin/
```

`make` is the default target and builds only the compiler. `make test` builds
`bin/nippy` and both test binaries, runs the compiler suite and the tool suite,
and exits non-zero if either fails.

Builds are parallel by default (one job per CPU). `make -j4` or `JOBS=4` sets
the count explicitly.

The test targets forward three variables to the runners, so one test or one
group runs without editing anything:

```sh
make test T=numeric          # tests whose "group: name" contains "numeric"
make test T="radix literals" V=1   # V=1 prints every test, with its time
make test J=2                # run two tests at a time
make test-list T=base64      # list matching tests without running them
```

There is no `install`, `dist`, or `check` target. Shipping is a prototype
concern that has not come up yet.

## Flags

```make
CC = cc
CFLAGS = -std=c11 -Wall -Wextra -Wpedantic -O2
```

All three warning flags are part of the contract. Code must build with **no
warnings**; a warning is a failing build in review even though Make will not
stop for it. Do not silence a warning with a cast unless the cast is genuinely
correct.

`-std=c11` appears twice by design and both must stay C11: `CFLAGS` builds the
compiler, and `build_binary` in `compiler/main.c` compiles the generated C with
`cc -std=c11`. Moving one to a newer revision without the other is a bug.

Overrides go through `make` variables rather than editing the file:

```sh
make CC=clang
make CFLAGS="-std=c11 -Wall -Wextra -Wpedantic -g -O0"
```

Note that overriding `CFLAGS` on the command line replaces the whole value, so
repeat the warning flags or you will lose the contract.

## What gets built

| Artifact | Built from | Purpose |
|---|---|---|
| `bin/nippy` | `$(COMPILER_SOURCES)` | The compiler and its command-line driver |
| `bin/compiler-tester` | `tests/compiler/*.c`, `tests/support/compile_support.c`, the harness, and the compiler minus `main.c` | The compiler suite |
| `bin/tool-tester` | `tests/tool/*.c`, `tests/support/tool_support.c`, the harness, and the compiler minus `main.c` | The tool suite |
| `bin/obj/` | One object (`.o`) and dependency file (`.d`) per source | Shared by all three binaries |
| `bin/<name>.c`, `bin/<name>.h` | Generated by `bin/nippy` | Generated C for `<name>` |

`COMPILER_SOURCES` lists every `.c` file explicitly — there is no wildcard over
`compiler/`, so **a new compiler module must be added to the Makefile** or it
will not build. `COMPILER_LIB_SOURCES` is `COMPILER_SOURCES` minus
`compiler/main.c`; both test binaries link that set so tests can call stages
directly, and neither links `main.c` because the harness supplies its own.

Test sources are the opposite: they are found by directory
(`tests/compiler/*.c`, `tests/tool/*.c`), so adding a test file needs no
Makefile edit.

Everything lands in `bin/`, which is git-ignored. Nothing generated is
committed.

## Incremental behaviour

Every source file is compiled once into `bin/obj/` and the objects are shared,
so the compiler is built once even though three binaries link it. Each object
has a `.d` file written by `-MMD`, so changing a header rebuilds exactly the
files that include it, and changing one source rebuilds one object and relinks.
Typical costs on a 12-core machine: a full clean build with both suites about
4 s, a rebuild after editing one test file about 2 s (almost all of it running
the suites).

Incremental *compilation* as a language feature (only recompiling the Nippy
module that changed) does not exist. It is tracked in `ARCH.md`'s "Known gaps"
section.

## Manual checks

Useful one-liners when the suites are not enough:

```sh
# Compile-check one unit without linking (needs -Iinclude; -fsyntax-only is fast)
cc -std=c11 -Wall -Wextra -Wpedantic -Iinclude \
  -fsyntax-only compiler/checker/checker.c

# Build the compiler with a different toolchain
make clean && make CC=clang

# Full rebuild, no warnings anywhere
make clean && make 2>&1 | grep -iE 'warning|error'

# Run a snippet without touching the repo
printf 'var x : Int32 = 13\n' > tmp/t.nip
./bin/nippy tmp/t.nip tmp/t && ./tmp/t

# Raise the default 4096-byte source limit
./bin/nippy --max-source-bytes 1048576 path/to/source.nip bin/program

# Inspect the generated IR
cat tmp/t.c tmp/t.h
```

Scripts, snippets, and scratch files belong in `tmp/`. See `AGENTS.md`.

## Test suites

There are two suites, each with its own binary:

- **Compiler suite** (`bin/compiler-tester`, `tests/compiler/`) — tests that run
  in-process: lexer, parser, checker diagnostics by topic, the analyser and
  generator stages, the public API, and the golden codegen tests. They pass
  source strings straight to `compiler_compile`.
- **Tool suite** (`bin/tool-tester`, `tests/tool/`) — tests that need other
  processes: runtime execution of generated programs (strings, collections,
  stores, numbers, traps), plus the driver, file I/O, the `cc` invocation, and
  the CLI allocation-failure sweep.

Each file under `tests/<suite>/` is a **group**: `tests/compiler/numeric.c` is
the group `numeric`. A test is addressed as `group: name`, and that is what a
filter matches. Add a test to the file whose topic it belongs to; a topic with
no file yet gets a new file.

`make test` runs both suites. Run it before calling a change complete. A
passing run is quiet — failures print with their captured output — and ends
with one summary line per suite:

```text
compiler-tester: 459 passed (459 of 459 tests, 0.21s, 12 at a time)
tool-tester: 136 passed, 1 todo (137 of 137 tests, 1.85s, 12 at a time)
```

A runner exits 1 if any test failed or errored, 2 if its filter matched no
tests, and 0 otherwise. A non-zero `todo` count is not a failure.

### The runner

Both binaries use the runner in `tests/harness/`. Run a binary directly for more
control than `make` offers:

```text
bin/compiler-tester [options] [filter...]

  -v, --verbose    print every test with its time, and passing tests' output
  -l, --list       list the selected tests by group and exit
  -j, --jobs N     run N tests at once (default one per CPU, or $NIPPY_TEST_JOBS)
  -x, --fail-fast  stop starting new tests after the first failure
  -t, --timeout S  kill a test after S seconds (default 120)
      --slowest N  list the N slowest tests
```

A filter is a case-insensitive substring of `group: name`; several filters
select a test if any matches. Run the tool suite from the repository root,
because it starts `./bin/nippy`, and so does the golden group, which finds its
files under `tests/compiler/golden/`. `make` always does.

Every test runs in its **own child process**. That isolates tests from one
another (no shared globals, no leaked allocation-failure hooks), turns a crash
or a hang into an error against the test that caused it, and lets tests run in
parallel. The cost is a fork per test, a few milliseconds.

Result kinds:

| Result | Meaning | Fails the suite |
|---|---|---|
| `TEST_PASS` | Behaviour is correct | No |
| `TEST_FAIL` | Behaviour is wrong | Yes |
| `TEST_ERROR` | The test could not run, crashed, or timed out | Yes |
| `TEST_TODO` | Decided but not yet implemented | No |

### How a test is written

A test is a function defined with `TEST("description")`, in the file for its
topic. There is no table, no `extern`, and nothing to register elsewhere:

```c
#include "compile_support.h"

TEST("a name that is not declared")
{
    return compile_fails("var x : Int32 = y\n", "an unknown name",
                         MESSAGE_CHECKER_UNKNOWN_NAME, "y");
}
```

`TEST` registers the function before `main` runs, using a GNU constructor
attribute that both gcc and clang accept under `-std=c11 -Wpedantic`. Tests
appear in each group in the order they are written in the file.

A test returns a `TestResult` and prints a short reason to `stderr` before
failing, so a red run says *why*. Helpers carry most of the weight:

- `compile_succeeds(source, expected_c, expected_h, what)` compiles `source` in
  memory and compares both generated artifacts byte-for-byte.
- `compile_fails(source, what, format, ...)` asserts `source` is rejected with a
  diagnostic containing `format` rendered with the remaining arguments.
- `compile_accepts(source, what)` asserts `source` compiles.
- `run_generated(source, expected, what)` (tool suite) builds the generated C,
  runs it, and compares standard output; `run_generated_failure` expects a
  non-zero exit and a diagnostic; `run_generated_driver` links a C driver.
- `expect_message(buffer, size, format, ...)` renders the expected text from the
  same macro the compiler uses.

Helpers live in `tests/support/`: `compile_support.*` for the compiler suite and
`tool_support.*` for the tool suite. A helper only one file needs stays in that
file as a `static` function.

### Message coverage is a rule

Every `MESSAGE_*` macro in `include/messages.h` must be named by at least one
test, and tests must assert against the macro rather than a hand-copied literal:

```c
return compile_fails("var x : Float = 13\n", "an unknown variable type",
                     MESSAGE_CHECKER_UNKNOWN_TYPE, "Float", "x");
```

This keeps wording and assertions from drifting apart. It also means a message
that cannot be reached from a test is a design smell: either the path is dead
code, or it needs a hook. Deleting an unreachable message is usually right.

### Test kinds

- **Golden codegen** (`tests/compiler/golden.c`) — see below.
- **Runtime semantics** (tool suite) — compile a source string with
  `compiler_compile`, write the generated C, build it with `cc` (renaming the
  generated `main` when a driver is linked), run it, and compare stdout. Used for
  tag tests, narrowing, and generic instantiations, which golden C alone cannot
  prove.
- **Driver** (tool suite) — write a `.nip` file and run `./bin/nippy`, because
  file I/O and the `cc` invocation are the subject.
- **Stage-level** (compiler suite) — include the stage headers and call
  `lexer_tokenize`, `parser_parse`, `checker_check`, `analyser_analyse`, or
  `generator_generate` directly. Used for internal and defensive messages that no
  source program can reach, by constructing a deliberately malformed artifact.
- **Allocation-failure** — arm `nippy_alloc_fail_after(n)` and prove each
  out-of-memory path reports and exits cleanly. The tool suite sweeps the CLI;
  the compiler suite injects a failure directly into `compiler_compile`.

### Golden tests

Each `tests/compiler/golden/NAME.nip` is a test. It is compiled, and the C
source and header it generates must equal `NAME.c` and `NAME.h` exactly. These
pin the generator's output, so they change whenever generated C does. A failure
reports the first differing byte.

- **Add one:** write `NAME.nip` (name it with hyphens: `a-generic-struct`), then
  run `make golden-update`.
- **After a deliberate generator change:** run `make golden-update`. It rewrites
  the expected files from the compiler's current output and lists the files it
  changed; review `git diff tests/compiler/golden` before committing, because a
  golden update is a statement that the new generated C is correct.

`make golden-update` rewrites only files whose content changed. It sets
`NIPPY_UPDATE_GOLDEN=1`, so it can also be run as
`NIPPY_UPDATE_GOLDEN=1 bin/compiler-tester golden`.

### Allocation-failure testing

`compiler/alloc.c` wraps `malloc`/`realloc` with a one-shot failure hook so
out-of-memory handling stays executable instead of untested.

- `nippy_alloc_fail_after(n)` lets the next `n` allocations succeed, fails the
  one after that, then disables itself. Failing exactly one allocation at a time
  is what lets a test observe the message that failure produces; a cascading
  failure would mask it by also failing the error-message copy.
- `nippy_alloc_reset()` (or `nippy_alloc_fail_after(NIPPY_ALLOC_NEVER)`)
  disables it.
- The driver honours the environment variable `NIPPY_FAIL_ALLOC_AFTER`, which is
  a test-only interface. It must stay unset in normal use.

Three tests use this: two in the tool suite (one sweeps every allocation index
through the CLI and asserts the compiler fails closed — non-zero exit, a
diagnostic, no binary left behind, no crash — and one proves each of the ten
out-of-memory messages is reachable in a single pass over the failure index), and
one in the compiler suite that injects a failure straight into
`compiler_compile`. The sweeps are the slowest tests in the suite, because they
start the compiler hundreds of times.

### Scratch files

A test that writes files calls `test_path("name")`, which names a file in a
directory private to that test. The directory is created on first use and
removed when the run ends, so tests never collide, can run in parallel, and
leave nothing behind. Files are never written into `bin/`, so a failed test
cannot leave a stale binary that a later test picks up. The compiler suite
rarely touches the disk: it passes source strings straight to `compiler_compile`.

## Tooling

| Tool | Used for | Notes |
|---|---|---|
| `cc` (GCC) | Building the compiler, building the test binaries, and compiling generated C | Default; the driver hardcodes `cc` |
| `clang` | Cross-toolchain check | `make CC=clang` builds and tests clean |
| `gdb` | Debugging | `make CFLAGS="-std=c11 -Wall -Wextra -Wpedantic -g -O0"` first |
| `clang-format` | Formatting reference | No committed config; match the existing style by hand |

Not available in the current environment, and therefore not part of the
workflow: **ASan/UBSan runtimes and Valgrind**. `-fsanitize=address` fails at
link time here because `libasan`/`libubsan` are not installed, and Valgrind is
absent. The allocation-failure sweep is what stands in for memory-fault
detection today. If a sanitizer runtime becomes available, adding a
`make test` variant that rebuilds with `-fsanitize=address,undefined` is the
obvious next improvement — do not document it as supported until it actually
links.

## Generated-code build

`compiler/main.c` writes the generated `.c` and `.h` beside the requested output
binary and then runs:

```sh
cc -std=c11 -o <output> <output>.c
```

Points worth knowing:

- The command is assembled as a shell string with single-quote escaping via
  `shell_quote`, so paths containing spaces or quotes survive.
- Only the `.c` is compiled; the `.h` is picked up through the emitted
  `#include`, which is why the header name is validated before being
  interpolated.
- The generated header is written first, then the source. A failure writing the
  source therefore leaves the header on disk, which is harmless because nothing
  links it.
- Generated code must compile cleanly under `-std=c11 -Wall -Wextra -Wpedantic`.
  That is why unused initialised variables get a `(void)name;` line: the
  generator, not the user, is responsible for warning-free output.
- The program's own `cc` invocation does not add warning flags; the clean-build
  property is verified by tests and by manual checks, not enforced at that step.

## Continuous integration

There is none. The suite is expected to be run locally with `make test` before a
change is called complete. If CI is added, the minimum useful pipeline is
`make clean && make && make test` on both GCC and Clang.

## Known build gaps

- No sanitizer or Valgrind coverage in this environment.
- No install target and no versioned binary.
- No CI configuration.
- Incremental compilation of *Nippy programs* (recompiling only the changed
  module) is not implemented. The repository's own build is incremental.
- The test runner needs POSIX (`fork`, `waitpid`) and a compiler that accepts
  GNU constructor attributes; it is not portable to Windows.
- Store runtime OOM is not executed by the suite: exhausting the host heap is
  not reliable in a test. The generated `nippy: out of memory` path is covered
  by inspecting the emitted runtime, not by running it out of memory.
